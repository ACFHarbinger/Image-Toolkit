**Root cause of "still slow + now freezes" — confirmed, not hypothesis:**

1. **#458 (fixed by me just now).** #444's cache-sizing fix never shrinks: `resize(max(current_maxsize, page_size))` ratchets upward forever. One directory opened with page size "All" permanently inflates the LRU cache for the rest of the process's life; the next large directory inflates it further. At max thumbnail size that's unbounded RSS growth — this is my top candidate for the actual freeze, and it correlates exactly with directory size the way Harbinger described. Added `LRU_CACHE_CEILING` (800), respects an explicit `§2.16B` user baseline instead of clamping it. 49 tests green.
2. **#453 — real regression, not fixed yet.** `5108db25` flipped `OpaqueViewport`'s `WA_OpaquePaintEvent` to `False` and made it fully transparent. That's the viewport of `MarqueeScrollArea` — every gallery. Combined with `937d4de8`'s app-wide unqualified `QWidget { background-color: transparent; }` rule (#457), there's no opaque widget left anywhere in the ancestor chain, so Qt can't use its fast scroll-blit path — every card repaint now walks the full tree to `MainWindow`. This is likely a large chunk of "feels slower than before," separate from #458's freeze.
3. **#454 — tuning, not a bug.** #444's fix (correctly) dropped the double-decode by connecting only `batch_result`, but that also means cards now render in bursts of 32 with only 2 chunks in flight against up to 8 threads. Perceived smoothness regressed even though total work went down.
4. **#455 — real bug, different symptom (hangs on quit, not on load).** Extractor tab uses `QThreadPool.globalInstance()` instead of a per-instance pool, unlike every other gallery tab (`gallery_base.py:85-96` explains why not to). Reproduced live today: `pytest gui/test/database/ gui/test/web/ gui/test/core/` hung indefinitely at extractor teardown. Codex flagged the test symptom as "pre-existing" while working #445/#447/#450 — that's probably right for the test itself, but the underlying bug is real and can hang the actual app on close with a large/corrupt video directory loaded.
5. **#456 — pre-existing, not from today.** `MetadataOverlay._load_metadata()` does a synchronous `os.path.exists()` + `QImageReader(path).size()` per card, on the GUI thread, during widget construction — before any async decode starts. For 1000 cards that's 1000 blocking disk reads up front. Likely a big piece of the *original* slowness, independent of anything landed today.

Nothing in today's suite could have caught #458 or #453. If anyone's adding tests for #453-457, a large-fixture or memory-budget test is worth the extra effort here specifically.
