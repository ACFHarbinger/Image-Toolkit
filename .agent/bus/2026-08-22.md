**`a326c417`'s new test itself was segfaulting the whole pytest process**,

commit right before this one, ran `test_wallpaper_scan_race.py` alone, clean
4/4 pass, no crash. Restored the new commit's version, same file, same
isolation — reliable segfault, even running just the one new test alone.

**Root cause, via a live gdb backtrace of a standalone repro** (not
guesswork): `test_settle_waits_for_gallery_workers_before_releasing_pending_switch`
monkeypatches `panel.thread_pool.activeThreadCount = lambda: next(active_counts)`
against a 2-item iterator. Something during `widget.close()`'s teardown path
(closeEvent's own checks) calls `activeThreadCount()` a third time →
`StopIteration` raised from inside a Python override reached via a C++
virtual call → segfaults in Shiboken's own exception-storage path
(`Shiboken::Errors::storePythonOverrideErrorOrPrint` → `PepException_GetArgs`)
instead of surfacing as a normal Python exception. Confirmed exactly this by
gdb `bt` on the crash. Separately (found while isolating), the test also
mutated the real `QTimer` class's `singleShot` staticmethod process-wide via
`monkeypatch.setattr(QTimer, "singleShot", ...)` — safe in principle since
monkeypatch restores it, but risky style since it's shared by everything
Qt does with timers for the rest of the test body; rebound the module-level
name inside `_scan_pipeline.py`'s own namespace instead, so only that
module's calls are affected.

**Fixed** (commit `2cc3e691`): `next(active_counts, 0)` instead of
`next(active_counts)`, plus the QTimer rebind above.
`test_wallpaper_scan_race.py` is 5/5 now; re-ran the full
`gui/test/{image,core,database,web,components}` sweep — **359 passed**, 0
failed, no crash.

**Note for whoever picks up the gallery-crash issue (#461) next**: this
StopIteration-through-a-virtual-override segfault shape is *not* the
gallery/dual-scan heap corruption class that issue tracks — it was purely a
test-authoring artifact (an exhausted mock iterator), reproduced and fixed
in isolation, unrelated to any production code path. Flagging only so it
isn't confused with #461 if this exact signature comes up again in a
different context — Shiboken exception-storage crashing on a Python
override's raised exception is a real fragility worth remembering
generally, just not this investigation's crash.
