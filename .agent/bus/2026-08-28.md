### Claude — 2026-08-28 (multi-phase renderer — design proposal for sign-off)

Scoped the multi-phase renderer for issue #463. Design writeup only, no code:
`.agent/reports/chat/asp_multiphase_renderer_design_2026-08-28.md`.

**Recommendation:** build **Option A — piecewise per-phase P1** — run the
existing `composite_plate_single_pose` once per `phase_spans()` span and join
the per-phase plates at the span boundaries, behind the existing default-off
`ASP_PLATE_SINGLE_POSE` (piecewise auto-engages only for multi-phase +
contiguity-check-pass). It is the only option that extends P1's clean-plate
benefit to the 60.8% multi-phase corpus, it is mostly composition of tested
code, and it is a concrete compositing-side down payment on M4's "phase-group
before alignment".

**Two things gate it, both in the doc, neither is code:**
1. *Validation first (§4).* Piecewise-band-stack assumes phase spans map to
   contiguous canvas `ty` bands. `phase_ids` is monotonic in *selection*
   order, not `ty` — and the §2.4 postmortem's finding (phase structure ≠
   camera-step structure) says don't assume it. Need a measurement: for the
   multi-phase RAW_ASP discriminating set (start with the sweep five), sort
   frames by `affines[i][1,2]` and check `phase_ids` monotonicity. Foldable
   into the next authorized Codex sweep. Decision rule in the doc.
2. *Spec decision (§5).* §2.3 (`ASP_PHASE_COMPOSITE`) already owns cross-phase
   seams in the legacy path. Piecewise P1 also acts at phase boundaries.
   Doc recommends: piecewise P1 owns boundary joins inside the plate path,
   §2.3 stays legacy-path-only.

Dropped the tempting "route P1-skip through §2.3" interim — its baseline is
unknowable without knowing whether Codex's `05/36/51/67/73` sweep had
`ASP_PHASE_COMPOSITE` set (it wasn't recorded).

**Open questions for Harbinger** in §7 (flag surface, compute ceiling /
`n_phases` cap, confirm §5a, validation scope, Option B disposition). Nothing
to implement until #1 clears and those are answered — steps 2–4 are then one
