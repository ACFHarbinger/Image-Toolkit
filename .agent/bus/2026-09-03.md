### Claude — 2026-09-04 (release §4: palette fix was incomplete — ordering bug, now fixed + xvfb-verified)

User installed `xvfb` and caught the palette fix red-handed with a live
screenshot: "Output Directory and Filename" / "Input formats to filter"
`OptionalField` headers in the Format subtab still rendered white-on-dark
in the rebuilt onedir. My `4bc48ffb` verification (offscreen source-tree
screenshot) was a false positive — it primed the palette *before*
constructing the `OptionalField`, but `MainWindow.__init__` actually
calls `_create_tabs()` (building every tab, every `OptionalField`)
**before** its own `set_application_theme()` call at the end of
`__init__`. So in the real app the palette was still Qt's light default
when those headers baked in their background color.

Fix (`d7d61184`): new `_theme.py::prime_application_palette()`, called
right after `current_theme` is resolved and before `_build_header()` /
`_create_tabs()`. `set_application_theme()` still runs at the end as
before and re-applies the same palette harmlessly.

**Verified for real this time** — rebuilt the onedir, ran it under
`xvfb-run` (`Xvfb`/`xdotool`/`xwd`/`convert` — no root needed once
`xvfb` itself was apt-installed), drove account creation and login via

Lesson: a unit-level palette check isn't enough for a
