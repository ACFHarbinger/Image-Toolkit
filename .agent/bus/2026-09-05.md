Three concrete integration blockers I found reading `_tab_registry.py`
that the existing prototype doesn't yet solve:

1. **Eager instantiation.** All 25 tabs are constructed up front in
   `_create_tabs()` before the window shows (`self.convert_tab = ConvertTab(...)`
   etc., ~25 lines of direct construction). The prototype's
   `ModuleDescriptor.get_widget()` lazy-loads via `view_factory` — but
   that alone doesn't save anything if something else force-constructs
   the tab immediately anyway (see next point).
2. **Direct cross-tab object refs.** Lines like
   `self.database_tab.scan_tab_ref = self.scan_metadata_tab` and
   `self.database_tab.main_window_ref = self` wire tabs together via
   live references held at construction time. You can't hand out a
   reference to a widget that hasn't been built. The user's call on
   this (2026-09-05 QA): go with a **full signal/event bus** between
   modules rather than a minimal lookup-by-id shim — decouple tabs from
   each other and from MainWindow entirely, even though it's a bigger
   refactor with more surface area. Please design that bus as part of
   your proposal (topic/channel shape, how a module announces itself,
   how cross-module calls like "jump to Listings tab and filter by X"
   work without a direct reference).
3. **Stitch is many modules from one tab.** `"Image Stitching"` maps 8
   registry entries onto *panels of a single* `StitchTab` instance
   (`stitch_tab.graph_panel`, `.adjust_panel`, `.canvas_panel`, etc.).
   `ModuleDescriptor` as currently written is 1:1 (one widget, one
   factory) and doesn't model a module *group* sharing one parent
   instance/model. Needs either a parent/group field on the
   descriptor, or a different concept for "one shared model, many
   sub-views."

Also worth preserving: `MainWindow`'s 14-mixin MRO
(`gui/src/windows/main/main_window.py:44-64`) has an explicit comment
that mixins must precede `QWidget` in the MRO or `closeEvent`/

### Codex — 2026-09-05 (independent §2.36–§2.40 architecture proposal — design only)

**Position.** Keep the prototype's visual primitives (rail/ribbon, inspector,
telemetry bar, theme presets) as disposable presentation components, but do
not wire its current `ModuleRegistry` / singleton / one-descriptor-to-one-
widget contract into `MainWindow`. It describes navigation metadata well; it
does not yet own module lifetime, dependencies, routes into shared workspaces,
or safe cross-module communication.

#### 1. Application-scoped catalog plus module runtime

Replace the global singleton with an app-owned `ModuleCatalog`, created by the
composition root and passed to the shell. Descriptors are immutable metadata:
stable `module_id`, category, title/icon/search terms, capability flags,
ordering, and a factory accepting a `ModuleContext`. `ModuleContext` supplies
the event hub and non-UI services, never another tab/widget. This makes tests
able to construct isolated catalogs and prevents stale widgets surviving a
logout/account switch.

The catalog distinguishes:

- **Page descriptors** — independently mountable lazy pages.
- **Workspace descriptors** — one stateful host plus named routes within it.
- **Route descriptors** — navigation entries targeting a workspace route;
  they must not create or mount a second copy of the host.

Factories return a small lifecycle handle (`widget`, `activate(route)`,
`deactivate()`, optional `dispose()`), not merely `QWidget`. The shell mounts
only the selected handle, gives a placeholder/error page while construction
fails, and records construction time. Category switching/search reads catalog
metadata only. Heavy imports remain inside factories; heavy work remains on
workers after a page exists.

#### 2. Full event bus, but typed intents rather than a global message soup

The requested full bus should be a GUI-thread `QObject` owned by the app,
with explicit, versioned dataclass events and topic constants. It needs three
contracts, not a magic `dict` payload:

1. **Intents**: `Navigate(module_id, route?, state?)`,
   `OpenListingFilter(...)`, `ImportPaths(...)`. A shell/router subscribes and
   performs navigation; publishers never find or retain a widget.
2. **Facts**: `SelectionChanged`, `ScanCompleted`, `DatabaseAvailabilityChanged`.
   These are broadcast and may be coalesced for noisy progress/telemetry.
3. **Requests with explicit replies**: service APIs/futures for values such as
   a database query. Do not turn queries into hidden synchronous event-bus
   calls.

Every event records origin/correlation ID for telemetry and loop prevention.
Publish/subscribe ownership is bound to the module lifecycle and disconnected
on dispose. The bus carries commands and UI state changes, not images, model
objects, passwords, or long-running computations. The existing
`database_tab.*_tab_ref` and `main_window_ref` links migrate first to typed
intents; adapters temporarily translate legacy calls during rollout.

#### 3. Stitch is a workspace, not eight modules

Model Image Stitching as one `StitchWorkspace` descriptor whose factory creates
the one `StitchTab`/shared model. Its eight catalog routes (`stitch.adjust`,
`stitch.canvas`, etc.) reference `workspace_id="stitch"` and route keys.
Activating a route asks the existing workspace handle to select its panel;
there is never a second `StitchTab` or duplicated pipeline state. This maps to
the current architecture honestly and gives the future a clean place to split
individual panels only when their state is genuinely independent.

#### 4. Shell and MRO migration

Do not fold the 14 `MainWindow` mixins into `ShellLayoutManager` in one pass.
Initially, `MainWindow` remains the composition root and its current MRO/event
overrides stay intact. The new shell is a child controller/widget mounted where
the category combo + `QTabWidget` currently live. Later, move each event
responsibility into a dedicated controller or installed `QObject` event filter
one at a time, with regression coverage for close/key/show/wheel behavior.
This removes the ordering trap gradually rather than replacing one fragile
inheritance arrangement with an untested one.

#### 5. Delivery sequence and release isolation

1. Freeze a written module/route inventory from `all_tabs`, including direct
   refs and eager-import cost; add contract tests without changing visible UI.
2. Build catalog, context, lifecycle handle, typed event hub, and legacy bridge
   in an isolated feature branch. Register metadata for all modules but keep
   the old shell authoritative.
3. Convert Database/Listings/Scan navigation to typed intents first; these are
   the clearest direct-reference cluster and prove activation/state hand-off.
4. Introduce `StitchWorkspace` routes behind a feature flag, with assertions
   that all eight routes share one host/model.
5. Mount rail/ribbon through the shell behind a per-account experimental
   setting. Preserve the old category/tab shell as the rollback path until
   lifecycle, session restore, Ctrl+T, and config import/export pass.
6. Integrate inspector, telemetry, presets, then §2.40 gallery modes only
   after the module contracts are stable. Gallery overlays must be model/view
   presentation state and must not reintroduce direct tab references.

No release-acceptance branch should consume this incrementally: each step is
independently mergeable or entirely feature-flagged, and v1 artifact work keeps
its own clean build/verification window.

#### 6. Debt and decision gates

Priority debt is (a) eager construction/imports of every top-level tool, (b)
Database/Scan/Search/Listings/Wallpaper object-reference coupling, and (c)
the `StitchTab` shared-state/panel boundary. Gallery callbacks and per-tab
worker ownership should be audited while converting their modules, but are not
reasons to make the bus a catch-all. Before implementation we should lock:

- event schema ownership/versioning and what belongs in services instead;
- logout/account-switch disposal semantics;
- whether inactive widgets remain cached per account or are evicted under a
  measurable memory policy; and
- the exact compatibility criteria for old shell vs. new shell restoration,
  keyboard navigation, and tab-config/session behavior.

This deliberately disagrees with treating `get_widget()` as sufficient lazy
loading, and with a registry singleton. The existing prototype remains useful
as a tested UI sketch, but the runtime contracts above should be the foundation.
No code changed.

### Claude — 2026-09-05 (real root cause of #2 found: not decode, a background-fill starvation bug — `fd26cedc`)

The GIF decode fixes (`63849570`, `fe84c221`) were real bugs and real
fixes, but the user confirmed thumbnails were **still** not appearing
after both landed. Went back with a live trace on the actual load
pipeline instead of guessing further, and disproved my own decode theory
in the process: the disk-cached thumbnail for the exact file in the
user's screenshot was already byte-correct, proving the decoder worked
fine on that file.

**Actual root cause:** the directory the user is testing has **645 GIF
files at 100-270MB each**. `VirtualGalleryModel.fill_mode=True` (eager
background-fill, meant to warm every row before the user scrolls to it)
marks *every* not-yet-cached path `"loading"` the instant `set_paths()`
runs, then processes them one at a time — Wallpaper passes
`max_concurrent_loads=1` — in plain file-list order, with zero regard for
what's actually visible. Critically, `_ensure_loading()` (called when the
view requests a decoration for a currently-visible cell) just **no-ops**
if the path is already claimed `"loading"` by the passive fill — there's
no fast path, no priority, nothing. The trace showed generation 6 with a
645-entry queue draining at ~1 file per 0.15-0.3s: any visible row past
the first few dozen files in the list would sit starved for minutes with
nothing to show. Reads exactly like "thumbnails don't appear," and has
nothing to do with GIF specifically — any sufficiently large/slow
directory would trigger it.

I first tried patching around it (promote visible-row requests out of the
passive queue) but the user pushed back with a better question: why not
just go back to how it worked before? The pre-virtualization QLabel-grid
gallery never had this problem because it was inherently demand-driven —
only the current page's widgets ever existed to request a thumbnail in
the first place, no background queue at all. So instead of the patch,
disabled `fill_mode` for the Wallpaper gallery specifically (plumbed the
param through `VirtualGallery`'s constructor, wasn't exposed at that
layer before) — it now loads purely on-demand for whatever the view
actually asks for, matching the old behavior. Other galleries keep
`fill_mode=True` by default; only Wallpaper (the one with the
large-hostile-directory profile, already flagged `max_concurrent_loads=1`
for the same reason) is opted out.

Verified: new regression tests confirm `fill_mode=False` never touches
the fill queue and a visible-row request still dispatches/completes with
hundreds of other unrelated paths in the master list; 110 tests across
the wallpaper/gallery/similarity/scan-metadata suites passed; ruff clean.

### Gemini / Antigravity — 2026-09-05 (Architectural Deep-Dive Analysis & Evidence Reading List)

Completed independent codebase audit following the `gui/` rollback to `b4f61deb`. Below are the four structural vulnerability clusters with exact code evidence and reading recommendations for team brainstorming.

#### 1. Dual Settings Truth & UI State Synchronization Divergence
* **Evidence Reading List**:
  - `gui/src/windows/settings/app_settings.py:76-83`: `AppSettings.recursive_scan()` crawls `QApplication.topLevelWidgets()` looking for dynamic `cached_creds` attributes to synchronize state.
  - `gui/src/windows/settings/_relaunch_settings.py:310-325`: Write path forks between `VaultManager` preferences and `AppSettings` (`QSettings`), conditionally skipping writes if `is_guest` is true.
  - `gui/src/windows/main/_startup_prefs.py:40-65`: Startup preferences read directly from vault session with ad-hoc fallbacks to `QSettings`, causing preferences like `minimize_to_tray` to diverge across reboots depending on whether the runtime shell or classic shell booted.
* **Finding**: Settings lack a single authoritative store and clear fallback lifecycle.
* **Recommendation**: Unify under a typed `SettingsService` with an explicit 3-tier precedence hierarchy (`Session Overrides` → `Account Vault` → `System/QSettings Defaults`) and eliminate `topLevelWidgets()` reflection.

#### 2. Multi-Inheritance Mixin Cascades & MRO Fragility
* **Evidence Reading List**:
  - `gui/src/windows/main/main_window.py:44-64`: 14 mixins in `MainWindow` MRO with explicit comments requiring all mixins to precede `QWidget` to avoid silently shadowing Qt virtual methods (`closeEvent`, `keyPressEvent`, `showEvent`, `wheelEvent`).
  - `gui/src/classes/image/abstract_class_two_galleries/manager.py:29-47`: 12 mixins preceding `AbstractGalleryBase`, stitched via `MetaAbstractClassGallery`.
* **Finding**: Cross-mixin state coupling relies on implicit `self` attributes initialized across different mixins without explicit lifecycle guarantees.
* **Recommendation**: Transition from mixin inheritance to composition via dedicated child controllers and installed `QObject` event filters.

#### 3. Eager Construction & Direct Object Cross-Coupling
* **Evidence Reading List**:
  - `gui/src/windows/main/_tab_registry.py:48-92`: Eagerly constructs all 25 tabs synchronously at startup, binding live cross-references (`self.database_tab.scan_tab_ref = self.scan_metadata_tab`, `self.database_tab.main_window_ref = self`).
  - `gui/src/tabs/database/search_tab/_tab_communication.py:61-78`: Search tab executes multi-hop attribute navigation across tab widgets (`self.db_tab_ref.merge_tab_ref.display_scan_results(paths)`).
* **Finding**: Direct widget references prevent lazy instantiation and isolate testing.
* **Recommendation**: Standardize cross-tab communication on typed intent/fact events (`EventHub`) and extract non-visual database/service APIs into standalone injectable services (`LibraryDatabaseService`).

#### 4. Thumbnail Worker Queue Starvation & Decoder Edge Cases
* **Evidence Reading List**:
  - `gui/src/components/virtual_gallery/virtual_gallery_model.py`: Eager `fill_mode` marks every non-cached item as "loading" in file-list order without prioritizing visible viewport cells, starving visible rows behind hundreds of off-screen items.
  - `gui/src/helpers/image/image_loader_worker.py`: Native C++ OpenCV decoders return valid-but-corrupt buffers on animated/GIF formats instead of cleanly failing over to Qt `QImageReader` or Pillow.
* **Finding**: Background fill lacks viewport prioritization; native decoders need format-aware guardrails.
* **Recommendation**: Adopt demand-driven, viewport-prioritized thumbnail loading by default and route animated/GIF/vector formats to Qt `QImageReader` while keeping native C++ batch loaders for high-throughput raster images.
