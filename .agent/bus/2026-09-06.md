
### Claude — 2026-09-06 (Extractor video-player regression #546: pointer + narrowed search space, no live time spent)

**If you're looking for the video-player investigation and don't see it here:** it was written to `.agent/bus/2026-09-05.md` on branch `fix/extractor-video-player-sizing` (not merged to `main`, so it wasn't visible from `main` or any other branch until this entry). **Canonical, branch-independent entry point: GitHub issue #546.** Read that first.

**Headless narrowing done just now (no live desktop needed, doesn't burn a debugging cycle):**

1. Grepped all of `gui/src/` for every writer of `video_item`/`video_view` geometry (`setSize`, `fitInView`, `setSceneRect`, `setTransform`, `setCacheMode`, `QGraphicsVideoItem`). Only `_media_player.py` and `_view_controls.py` touch it — no undiscovered third code path. That hypothesis from the original bus post is now ruled out.
2. Traced the actual construction/load sequence and found a real, previously-undocumented candidate for the "verified-correct write side, still wrong on screen" mystery:
   - Session-recovery restore (`_config_methods.set_config`) uses `load_media(..., defer_player=True)`, which deliberately leaves the `QMediaPlayer`/`QGraphicsVideoItem` **unconstructed** (issue #81: constructing it during the startup burst aborts the process). The video only actually loads on the user's **first Play press** (`toggle_playback()` calls `load_media(path, force=True)`), not on tab click alone.
   - In `_apply_player_mode()`, `media_player.setSource(...)` runs *before* `media_player.setVideoOutput(self.video_item)` — the latter is also the first access to the `video_item` property, which is where it gets constructed and `nativeSizeChanged` gets connected (once, for the whole widget's lifetime — the same item is reused across every video/tab switch, never recreated).
   - `change_resolution()` (called synchronously right after, in the same `_apply_player_mode()` call) invokes `fit_video_in_view()` immediately — almost certainly before Qt Multimedia has probed the stream, so `native_size.isEmpty()` is still true at that point and this call is a no-op for sizing.
   - The real resize is supposed to come later, asynchronously, off `nativeSizeChanged`. Two untested-but-plausible failure modes for that path specifically (narrower than the original 4 open hypotheses):
     - **Qt only emits `nativeSizeChanged` on an actual value change.** If the item's native size was already left at some prior value (e.g. from a previous video, or a stale default) that happens to already equal the new video's size, the signal never fires and `fitInView()` is never re-run with correct geometry.
     - **Timing race with visibility/layout.** `video_view.setVisible(True)` happens earlier in the same `_apply_player_mode()` call; if `nativeSizeChanged` fires before Qt has actually laid out the now-visible view (viewport size still stale/zero), `fitInView()` scales against the wrong viewport rect. `resizeEvent` is the only backstop that would re-run `fit_video_in_view()` afterward, and only fires if Qt's layout pass produces an actual size change after that point — not guaranteed to happen if the initial geometry Qt assigns during show already matches the final size.
   - Neither of these has been confirmed — they're the narrowed starting point for whoever picks up #546, not a diagnosis. The next live step (needs the desktop, do this before anything else): log `video_item.size()`/`boundingRect()` and `video_view.transform()` **read back after a repaint**, not just at the moment `fit_video_in_view()` sets them — nobody has confirmed the paint-time values match the write-time ones yet.

Not resuming solo iteration on this per the user's explicit instruction to bring in a fresh team — this is pre-dispatch context-gathering only, done without touching the live app.
