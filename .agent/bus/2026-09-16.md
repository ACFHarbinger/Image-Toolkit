### Claude — 2026-09-16 (round 7 result + round 8 fix -- SQLCipher/libsodium linker search path, #471)

Seventh dry-run (run 35149296696) got past all four round-6 compile
errors with no recurrence (real progress), but `build-windows` failed
at the link stage:

```
LINK : fatal error LNK1181: cannot open input file 'sqlcipher.lib'
```

Root cause, found in `base/CMakeLists.txt` and `base/tests/CMakeLists.txt`:
both pass bare library names (`sqlcipher`, `sodium`) to
`target_link_libraries` and a hardcoded `/usr/lib/x86_64-linux-gnu` to
`target_link_directories`. This only ever worked on Linux because that
directory is a default system linker search path -- `pkg_check_modules`
genuinely does find vcpkg's `sqlcipher.pc` on the Windows runner
(confirmed in the log: "base: SQLCipher + libsodium found"), but
MSVC's linker has no equivalent default search path into vcpkg's
install tree, so it never sees the `.lib` file pkg-config pointed at.

Fix: link against `${SQLCIPHER_LIBRARIES}`/`${SODIUM_LIBRARIES}` (same
bare names on Linux, so no behavior change there) and add
`${SQLCIPHER_LIBRARY_DIRS}`/`${SODIUM_LIBRARY_DIRS}` via
`target_link_directories` -- `pkg_check_modules` populates these with
the actual containing directory on every platform, including vcpkg's
on Windows. The literal `/usr/lib/x86_64-linux-gnu` and `/usr/include`
paths are now gated behind `if(NOT WIN32)`, since they were never
needed given the `LIBRARY_DIRS` variables exist. Commit `debc02a5` on
`feature/471-windows-build`.

Verified locally: `base/CMakeLists.txt` on this branch already had
vcpkg `PATHS` entries in the `find_path`/`find_library` fallback block
(presumably from an earlier round I hadn't re-read since); my fix
merged cleanly alongside it via `git stash`/`checkout`/`pop`. Full
`base` CMake target reconfigures and rebuilds clean on Linux (exercises
the same `pkg_check_modules` path Linux always used, now routed through
the `LIBRARY_DIRS` variable instead of relying on the OS default search
path coincidentally matching).

### Claude — 2026-09-16 (round 8 result + round 9 fix -- BASE_BUILD_TESTS=OFF for the CI release build, #471)

Eighth dry-run (run 35152366832) got past the SQLCipher/libsodium
linker fix -- both `base.pyd` and `base_tests.exe` linked successfully,
no `LNK1181` recurrence, confirming round 7's fix worked. New failure,
at the very last build step:

```
CMake Error at .../CatchAddTests.cmake:81 (message):
  Error running test executable 'tests/base_tests.exe':
    Result: Exit code 0xc0000135
```

`0xc0000135` is `STATUS_DLL_NOT_FOUND`. CMake's `catch_discover_tests`
runs the test binary at *build* time (not as a separate ctest step) to
enumerate its test cases, and `base_tests.exe` can't find a runtime DLL
on the runner (most likely vcpkg's `sqlcipher.dll`/`libsodium.dll`,
installed to `C:/vcpkg/installed/x64-windows/bin`, which isn't on
`PATH` for this step).

The release workflow packages the app; it was never meant to build or
run the native test suite. `build-linux` already avoids this because it
goes through the `build-base` just recipe (`tools/build/justfile`),
which passes `-DBASE_BUILD_TESTS=OFF` -- that's why this never surfaced
there. `build-windows` invokes `cmake` directly and never set the flag.
Fix: pass `-DBASE_BUILD_TESTS=OFF` in `.github/workflows/release.yml`'s
Windows cmake configure step, matching `build-linux`'s existing
behaviour. This is gated cleanly in `base/CMakeLists.txt:343-346` --
`add_subdirectory(tests)` (and therefore `catch_discover_tests`) is
entirely skipped when the option is off, so no source change is
needed. Commit `f5e6f83e` on `feature/471-windows-build`.

Workflow-YAML-only change -- no local rebuild needed to verify (the
`add_subdirectory(tests)` gating was confirmed by reading the CMake
option definition directly); actual verification is the next dry-run.

   it's security-sensitive).

   `std::partial_sort` calls elsewhere -> `NOMINMAX`/

   `_popen`/`_pclose` remap in `wallpaper.cpp`.
8. `target_link_libraries(base PRIVATE sqlcipher sodium argon2)` used
