**Incident, for anyone else working in the shared checkout:** building
PR #717 the first time, I ran `git submodule update --init submodules/ASP`
inside a *separate worktree* added from `origin/main`, then `cd`'d into
that worktree's `submodules/ASP` and ran `git remote set-url origin
<ASP-repo-URL>` + `git fetch origin main` to move the gitlink to ASP's
latest commit. Because of how submodule gitdirs resolve under a linked
worktree in this checkout, that remote-url change and fetch landed on the
*superproject's own* `origin` remote and `refs/remotes/origin/main` --
silently repointing them at the ASP repo and overwriting `origin/main`'s
SHA with ASP's tip. This is shared state (one object DB / ref namespace
across every worktree off this repo), so it would have corrupted
`origin/main` for every worktree and the shared checkout itself, not just
mine.

Caught it immediately (a `git worktree add` from `origin/main` landed at
an ASP commit with no `submodules/` directory at all) and fixed in place:
`git remote set-url origin https://github.com/ACFHarbinger/Image-Toolkit.git`
then `git fetch origin main` restored both the remote and the ref
(reflog confirms: `...de6cafd2 -> 71af1bcf(bad) -> de6cafd2(restored)`).
Verified `git fsck` afterward -- only ordinary dangling objects, nothing
else broken; shared checkout's branch/uncommitted edits were untouched
throughout. Redid the actual submodule bump with
`git update-index --cacheinfo 160000,<sha>,submodules/ASP` instead
(no submodule checkout needed for a pure gitlink bump) -- clean the
second time.

**Lesson for future bumps:** never `git submodule update --init` +
`cd`/`remote set-url` + `fetch` inside a submodule path from a linked
worktree to move its pin. Use `git update-index --cacheinfo
160000,<target-sha>,<path>` against the superproject tree directly, or
`git -C submodules/ASP fetch <url> <ref>` with an explicit URL (never
`remote set-url`) if you need the submodule's own history materialized.
