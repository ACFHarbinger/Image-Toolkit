
### Mistral — 2026-10-15 (512px gauge redesign — approach chosen, claiming)

Per Harbinger's "once you choose an approach" — the flags wiring is on
draft #812 (no review yet), so I'm taking the deferred piece: making
the #756 gauge fit at 512px. Branch `feat/gauge-probe-scale` off
`main`, worktree `~/Downloads/Data/Tests/dl-gauge-probe-scale`.

**Why not gradient checkpointing:** the memory hog is the
`create_graph=True` backward, and a checkpointed forward doesn't help
there — the recompute during the graph-building backward must itself
retain the recomputed activations as nodes of the gradient graph, so
the ~7.3 GiB transient (measured, #756 validation) barely moves while
adding double-backward-through-checkpoint risk.

**Chosen approach — `hessian_probe_scale`:** the gauge's frozen probe
batch is built at a downscaled resolution (area-interpolated latents,
factor 1/scale; noise/timesteps drawn at the scaled shape from the
same validation_seed; conditioning unchanged). The trace series stays
deterministic and comparable across checkpoints — the exact property
the gauge needs; what changes is that curvature is measured on a
256px-equivalent probe when training at 512. Default `1` = today's
behavior; the 12 GB laptop recipe is `2`. Documented openly: it is a
probe-scale curvature measurement, not the full-resolution trace, and
runs with different scales are not comparable to each other. No
checkpointing, no estimator changes — the proven Hutchinson machinery
is untouched; only the frozen batch's resolution is parameterized.

Deliverables: `freeze_eval_batch(probe_scale=…)`, scale recorded in
`FrozenEvalBatch`/report, `hessian_probe_scale` config field +
base.yaml declaration + `_build_tuner` passthrough, CPU exactness
tests (shapes/determinism/interpolation), one GPU smoke at true 512px
training with scale 2 proving the gauge logs at every checkpoint with
the peak measured (scale 1's OOM is already documented from two prior
validation runs), changelog, PR.
