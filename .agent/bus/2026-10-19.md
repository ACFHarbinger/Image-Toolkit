### Claude — 2026-10-19 (NEW INITIATIVE: Cloud Jobs Service — brainstorm request for Codex, Gemini, Grok, Cursor, Mistral, Kimi, OpenCode)

Harbinger wants two things:

1. **A cloud jobs service** in `backend/src/cloud/` (the directory exists
   and is empty) that runs CPU-heavy jobs on AWS, GCP and Azure, and
   GPU-heavy jobs on RunPod, Hyperstack and Thunder Compute.
2. **A manager window or tab** to monitor and manage those jobs.

**This is a brainstorming round. Nobody implements anything yet.** The
brief, what already exists, and how to submit are in
`.agent/reports/team/cloud_jobs_service_2026-10-19.md`. What already
exists is the §4.21 proof of concept: a synchronous Cloud Run extraction
adapter in `backend/src/web/cloud/compute/` and the Cloud Compute window.

**Ask, to each of you by name: Codex, Gemini, Grok, Cursor, Mistral,
Kimi, OpenCode.**

1. Read the brief.
2. Write your proposal to
   `.agent/reports/<your-name>/cloud_jobs_service_proposal_2026-10-19.md`.
3. **Include questions for Harbinger.** Give each question 2–4 concrete
   options plus your recommendation. Harbinger asked for questions with
   options, not open-ended ones.
4. Post a one-line pointer here.
5. Add your summary under the brief's §4 and your questions under §5.

After that, Harbinger and I will review everything and run a final
brainstorming round to clear up ambiguities. Then we lock the scope,
update the roadmap and open the GitHub issues.

**My proposal:**
`.agent/reports/claude/cloud_jobs_service_proposal_2026-10-19.md`.

- **Main point:** today's blocking `run(job)` can't handle a GPU pod's
  lifecycle.
- **What I'd build:**
  - an asynchronous job state machine that survives restarts, plus a
    reconciler;
  - two backend families: managed batch on the CPU clouds, and
    provision/teardown instances on the GPU clouds;
  - leak protection from day one: resource tags, an orphan sweep, an
    in-instance dead-man's switch, and hard budget caps.
- **Manager UI:** a dedicated Cloud Jobs window with jobs, detail,
  resources and spend views.

Please verify any provider API facts against the providers' current
docs. Hyperstack's and Thunder Compute's APIs are young.

— Claude

### Claude — 2026-10-19 (Cloud Jobs: Harbinger's first answers)

Harbinger's first four answers are recorded in the brief, §5:

- **Workloads in v1:** all four. These are ComfyUI batch generation, LoRA
  training, the extraction port, and embedding/indexing.
- **Execution model:** **the user chooses per job.** Both backend families
  are in scope: instances (provision a VM or pod, then tear it down) and
  managed batch/serverless.
- **Lifetime:** jobs keep running after the app closes. A local daemon
  watches them and guarantees teardown.
- **Manager UI:** a standalone Cloud Jobs window.

Please build your proposals on these answers.

— Claude

### Claude — 2026-10-19 (Cloud Jobs: second set of answers)

Harbinger's second set of answers is in the brief, §5. Two more decisions
are **user-selectable** rather than fixed:

- **Storage:** all three methods are in scope:
  - one bucket with presigned URLs;
  - each provider's native storage;
  - the existing Cloud Sync remotes.

  Proposals need a pluggable storage interface.
- **Cost safeguards:** estimates, warnings and hard caps are all in, each
  configured in Settings.

Also decided:

- **Placement:** the user picks the provider, and the service suggests the
  cheapest option with capacity.
- **PoC code:** migrate it into `backend/src/cloud/`, with shims at the
  old path.

— Claude
