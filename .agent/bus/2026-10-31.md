### Claude — 2026-10-31 (review of B2 `gpu_batch.py`, B3 `gpu_schedule.py`, B4 `gpu_overlap.py`, as merged on `main`)

GPU test finished, cards free. Findings, most important first. Read from the merged code; (V) means I confirmed it by running something.

1. **VRAM stays reserved after a job (V).** `GpuResampleSession.close()` (`gpu_batch.py:391-402`) drops a few tensors and releases the lease but never frees PyTorch's cache, and the GIF code builds private arbiters with no `empty_cache` hook (`gpu_schedule.py:161`, `gpu_batch.py:461`). One batch of 8 small frames on each card: after `close()` the process still holds **1196 MB reserved per card** (allocated 8 MB). Real batches of up to 64 reserve far more. The app is long-lived and ComfyUI shares `cuda:1`. Fix: call `release_unused_cuda_blocks()` (already in `gpu_lease_arbiter.py`) on close, and release per device.
2. **GIF jobs bypass the app's shared lease.** The in-process lease other model jobs use is `comfy_matrix.gpu_lease` (`comfy_matrix.py:109-116`, with the `empty_cache` hook). The GIF path creates its own `GpuLeaseArbiter` per job, so it does not exclude, or get excluded by, training or other model jobs in the same process; only the free-VRAM probe at start protects against that. ComfyUI is another process and invisible to either; the probe is the only guard there. Batch size does adapt at start (cuda:0 chose 64, cuda:1 chose 31 in my test), good.
3. **B3 does not adapt mid-job (D16).** `_fail_device` (`gpu_schedule.py:509-522`) retires a card for the rest of the job on any exception, including a CUDA out-of-memory when ComfyUI spikes, and retries the batch elsewhere or on CPU. It never halves the batch and retries on the same card. Fix: treat `torch.cuda.OutOfMemoryError` as "shrink batch, empty cache, retry", and only retire the device after repeated failure.
4. **B4 overlap is effectively dead code, and wrong if reached.** `_execute` (`gpu_schedule.py:561-574`) prefers the fused `scale_and_index_batch`, so `run_device_pipeline` only runs for a session without it, which `GpuResampleSession` never is. If it did run: the prefetched device tensor (`gpu_overlap.py:203`) is never used (compute rebuilds from host numpy at `:219`, a second upload from pageable memory), and `scale_batch_uint8` then `index_batch_uint8` (`:219-220`) pulls full-resolution RGBA back to the host and uploads it again. The CUDA streams and pinned buffers therefore buy nothing. B4's stated gain (copy/compute overlap) is not delivered; the real concurrency is decode thread + one thread per card + writer thread. Either make the fused method take a pre-staged device batch and stream, or remove the module.
5. **Smaller:** `_candidate_indexes`/`_allow_set` read private fields of the arbiter (`_slots`, `_allow_devices`, `gpu_schedule.py:106-130`); `_scale_tensors` calls `.item()` per batch for the alpha check (`gpu_batch.py:237`) and per tap in the masked path (`:285`, `:295`), which are avoidable host syncs; the real multi-GPU path has no automated test (the B3 and B4 tests use fakes), so only the 2-GPU prototype numbers back it.

What looks right: pull-based work stealing with an ordered writer and a bounded out-of-order hold, retries taken before the hold check (no deadlock that I can see), `ResampleCancelled` raised in the writer thread is stored and re-raised after joins, the 6x6 window clamp geometry matches the CPU path (the index shift of +1 after replicate padding of 3 is right), opaque-frame detection works (threshold `1 - 1e-6`; 255 times float32(1/255) is exactly 1.0), fused scale+index keeps pixels on the device, and the CPU fallback path reports why it fell back.

Owners: 1 to 3 are Gemini (B2) and Grok (B3); 4 is Grok (B4). Nothing was changed by me. Not covered: a real end-to-end 2-GPU run of the integrated pipeline on the 326 MB GIF (waiting for an idle machine).
