# ADR-0008: Zero-Copy C++ Thumbnail Streaming (`asset://`) and Shared WebGL2/WebGPU Canvas Host

- **Status:** Accepted (Locked 2026-10-19)
- **Tracking:** [#887](https://github.com/ACFHarbinger/Image-Toolkit/issues/887), [#888](https://github.com/ACFHarbinger/Image-Toolkit/issues/888), [#902](https://github.com/ACFHarbinger/Image-Toolkit/issues/902)

## Context

Base64-encoding high-resolution images or 100k-item gallery thumbnails over JSON-RPC stdio saturates IPC bandwidth and blows up webview heap memory. Similarly, multiple editors (Merge, Extractor frame-slicing, ASP Stitch, HIE, and CSG Manga) require zoomable, pannable multi-layer canvases that cannot scale on DOM/2D-canvas nodes alone.

## Decision

1. **C++ thumbnail service + `asset://` streaming (#887):**
   - Gallery stills are generated by the C++ `backend` thumbnail service as bounded JPEGs (extracting the **middle frame** by default for videos/animations) written to `~/.image-toolkit/cache/render/`.
   - The webview streams rendered stills directly via Tauri's `asset://` protocol; original library files are never placed in `asset://` scope, and large images are never base64-encoded over stdio.
   - Animated hover/scrub preview is a separate, cancellable request.
2. **Shared WebGL2/WebGPU tile-pyramid canvas host (#888, #902):**
   - All canvas-heavy capabilities (Merge, Extractor, Stitch, HIE, CSG) share a single canvas host built on a WebGL2/WebGPU tile pyramid.
   - An off-screen worker performs viewport culling and requests level-of-detail (LoD) tiles asynchronously.

## Consequences

- 100k-item virtualized galleries mount in tens of milliseconds without exposing raw user directories to the webview.
- Editor capabilities share one GPU-accelerated viewport implementation instead of maintaining separate canvas stacks.
